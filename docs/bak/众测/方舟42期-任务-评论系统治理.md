```text
================== 需求：评论系统治理（反垃圾评分 + 审核状态机 + 站长通知）==================

背景现状（仅作导航，阶段 1 仍必须实读代码核实，不得以此代替探查、不得臆断字段名）：
- 评论链路：src/app/api/comments/route.ts（GET ?postId= / POST）→ src/services/notion.ts
  （getCommentsByPostId / addComment；Notion 评论库 + 本地 localComments 双 fallback）。
  本地兜底数据在 notion.ts 内 localComments 与 src/data/comments.ts 双份存在，CommentType 接口两处重复定义。
- POST 现状：无限流、无反垃圾、无审核状态、无任何通知；GET 返回该文章全部评论。
- 可复用设施（先读再复用，不要重复造轮子）：
  · src/lib/rateLimit.ts——内存限流（10 次/分/IP），已用于 /api/subscribe*，评论路由未接入；
  · src/services/email.ts——Resend 封装，无 RESEND_API_KEY 时降级 console.log 返回 { ok:false, skipped:true }；
  · src/lib/adminAuth.ts evaluateAdminAccess——ADMIN_TOKEN 鉴权纯函数（已配 vitest 测试，含伪造 host 用例）；
  · /admin/content 与 /admin/notify 后台页面模式 + src/lib/adminMessages.ts i18n 模式；
  · vitest 已就位：vitest.config.ts + src/lib/__tests__/ 四个测试文件，`npm test` 真实跑测。

1. 反垃圾评分引擎（新建 src/lib/spamScore.ts，纯函数，便于单测）
   - 输入：作者（name/email）+ content + 可注入的规则配置；输出 { score: 0-100, reasons: string[] }。
   - 至少覆盖以下规则（权重自定，但必须在 spec 中说明依据）：
     正文链接数量与占比、垃圾关键词黑名单（可配置，en/zh 双语词表）、全大写字母占比、
     连续重复字符/重复行、内容过短或无意义堆砌、可疑邮箱域名/TLD、同一邮箱短窗口高频提交。
   - 阈值钉死：score>=70 自动判 spam；30<=score<70 进 pending 待人工审；score<30 直接 approved 即时可见。
   - 阈值与规则配置支持依赖注入（默认值内置）；纯函数不得依赖真实时钟/网络/进程内共享状态
     （频率类规则以可注入的计数接口实现）。

2. 审核状态机（数据层，src/services/notion.ts）
   - 阶段 1 实读 notion.ts 评论相关实现与 Notion 评论库字段结构，不得臆断。
   - 新增评论状态：pending | approved | spam。
     Notion 评论库需用户手动新增的字段（如状态 select、分值 number、命中原因 rich_text）
     在 spec 中列出（HITL-1 决策点）；代码对字段缺失做防空：
     旧数据无状态字段一律兜底为 approved（存量评论全部保持可见，不因升级而消失）。
   - 新增流转函数 setCommentStatus(id, status)（经 Notion API 更新 + 本地 fallback 双实现）。
   - 查询改造：前台 getCommentsByPostId 只返回 approved。注意两个易漏点：
     a) 嵌套回复树的过滤——spam/pending 的子回复不得随树吐出；
     b) 本地双份 fallback 数据（notion.ts 的 localComments 与 src/data/comments.ts）都要同步改造。
   - 为后台新增全量查询（含三态，带分页或数量上限防大库拖垮）。

3. API 改造（/api/comments）
   - POST 流水线：接入限流（复用 src/lib/rateLimit.ts，超限 429 + i18n 文案）→ 评分引擎打分 →
     按阈值落三态写入 → 按状态触发站长通知 → 返回响应。
   - 响应语义：approved 正常返回评论对象；pending 返回明确的「已提交、待站长审核」提示（i18n）；
     spam 的返回体不得向前台泄露判分与命中原因细节（防机器人探测阈值；返回体如何设计在 spec 中说明取舍）。
   - GET：仅返回 approved（含回复树过滤），pending/spam 一律不可见。
   - 输入校验与错误处理完整，不吞异常。

4. 站长通知
   - pending 与 spam 的新评论触发站长邮件（复用 services/email.ts 的模式与降级行为，不另起炉灶）：
     含所属文章、作者、内容摘要、命中原因（仅站长可见）、/admin/comments 审阅链接。
   - 站长收件人用环境变量配置（如 COMMENT_NOTIFY_TO）；未配置或无 RESEND_API_KEY 时
     降级 console.log 完整信息，通知失败绝不阻塞评论主流程。

5. 审核工作台（新建 /admin/comments，复用现有 /admin 体系）
   - 鉴权沿用 evaluateAdminAccess 语义：ADMIN_TOKEN 已配置则必须校验；未配置时仅本地放行 + 控制台告警。
   - 流转走新建的 /api/admin/comments/* 路由（同样鉴权），支持 curl 验证。
   - 页面：全量评论列表（pending/spam/approved 三态筛选 + 待审/垃圾计数徽标），
     显示评分与命中原因；操作：approve / 标 spam / 打回 pending；approve 后前台立即可见。
   - en/zh 文案接入 next-intl（参照 adminMessages 模式），深色模式 + 移动端可用。

6. 前端组件（CommentSection/CommentList/CommentForm）
   - 提交后按三态返回展示对应反馈：已发布（即时出现在列表）/ 待审核（明确提示）/ 限流或失败（可重试提示），
     全部 i18n，不硬编码文案。
   - 列表仅渲染 approved；被审评论不占位、不闪烁。

7. 单元测试（阶段 5 走 A 路径，必须做；vitest 已就位，无需引入）
   - TDD 红绿，至少覆盖：
     a) spamScore：各规则独立命中各得正分、正常评论 <30、边界 29/30/69/70、阈值与配置注入生效；
     b) 状态过滤：pending/spam 不出现在前台列表——含嵌套回复树、含本地双份 fallback、含旧数据无字段兜底 approved；
     c) POST 三态分流：mock Notion 写入，断言落库状态、响应语义、spam 响应不泄露 score/reasons；
     d) 后台流转与鉴权：复用 adminAuth 既有测试模式，覆盖无 token / 错 token / 未配置三态。
   - `npm test` 必须真实跑通且 total_tests>0，输出贴进 ci_result.md，不得虚构。
```

```text
【评论系统治理 - 评估维度与判定标准】

评估维度（5 项，权重从前到后递减）：
1. 三态审核与前台过滤（权重最高）：score<30 即时可见、30-69 待审、>=70 判垃圾，阈值边界正确；

   POST 对 spam 的响应不向前台泄露判分细节（防机器人探测）；限流接入 POST（超限 429）。
3. 审核工作台：/admin/comments 三态筛选列表 + 待审/垃圾计数徽标 + 流转（approve/标垃圾/打回），
   approve 后前台立即可见；鉴权沿用 ADMIN_TOKEN 语义（未配置仅本地放行+告警，不抛错崩溃）。
4. 站长通知与无 Key 降级：pending/spam 触发站长邮件（复用现有 email 服务模式），
   无 RESEND_API_KEY / 未配置收件人时降级 console.log 且不阻塞评论主流程；
   沙箱无任何密钥时全链路 npm run dev:env 可跑不崩。
5. Harness 流程与测试：十阶段完整走、评审 v1 REJECTED->v2 真实回退（非走形式）、
   产出物落 .harness/changes/feat-comment-moderation-20260828/、门禁贴 lint/build/test 真实输出；
   vitest 覆盖评分规则与边界(29/30/69/70)、状态过滤三易漏点、POST 三态分流、后台流转鉴权，
   npm test 真实跑通 total_tests>0。

【优秀（S/A 档，9-10 分）】
- 5 个维度全部达标，无 P0/P1 缺陷；
```
